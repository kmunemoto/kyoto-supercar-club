# システムレビュー（2026-08-29）

「この事業を支えるシステムをどう評価するか、変えるべきものはあるか」への回答。6 の分析エージェント（技術スタック適合性 / リード業務システム / 将来の車両運用システム / 事業メカニズム、＋反証・完全性チェック 2）で評価し、反証で却下・修正された主張を反映済み。金額・ルールはすべて `content.ts` 掲載値から引用し、推測は推測と明記する。

## 結論の要約

- **技術スタックは変えなくてよい。** 作り直し・移行の提案はすべて反証で却下。実質的な弱点はコードの外にある——①独自ドメイン不在、②LINE が CRM の外、③リード DB が実質単一コピー。
- **事業メカニズムは開示姿勢が高水準な一方、公開中の数字に構造的な弱点が 2 つある**（OWNER NETWORK の受け渡し単価、VALUE CHECK の固定費フロア）。`FEE_NOTE` が「未確定」と明示している**今なら低コストで変えられる**。
- **将来の車両運用は「作らない」が正解。** `future.sql` の 16 テーブルが暗示する自社開発路線は車両 1〜3 台に対して過大。予約は人手＋カレンダー、決済はホスト型 Stripe、GPS は SaaS 購入、契約は電子契約 SaaS。

## 1. 技術システム — 維持。ただし前提条件が 3 つ欠けている

### 変えなくてよいもの（作り直し提案はすべて却下）

- **TanStack Start SSR + Lovable Cloud**: 依存 19 個まで削減済み。SSR は canonical/sitemap/OGP 生成とサーバー側フォーム処理（secrets をクライアントに出さない）に実際に使われており、静的サイト＋外部フォームに落とす方が構成要素が増える。
- **ロックインは薄い**: nitro が Cloudflare Workers 標準形式（`wrangler.json`）を出力し、マイグレーション 10 本が git に完備。コードとホスティングの脱出路は実在する。唯一の不確定要素はデータ（下記③）。
- **リード防衛の多段構え**（`rescueUnsavedLead` / `insertWithFallback` / `notification_log` / 送信タイムアウト）、CI、マージ規律、supply-chain ガード（`minimumReleaseAge`）。

### 欠けている前提条件（優先順）

1. **独自ドメイン + Resend ドメイン検証**（今すぐ・経営判断）
   `NOTIFY_FROM` 未設定の既定値は Resend サンドボックスで、**アカウント所有者以外に届かない**。つまり実装済みの受付控え・運営通知は現状ほぼ無効。重要: **ドメイン検証はサイト公開前にメールだけ先行できる**。ドメイン名を決めれば、サイト移行を待たずにメールが本物になる。SEO 資産が lovable.app に蓄積し続けている問題も同根。
2. **main 直行経路の保護**（今すぐ・小）
   Lovable エディタ（AI 編集含む）の変更は AGENTS.md の検証フローを通らず main → 公開プレビューに直行する。GitHub 側の branch protection（人間経路の CI 必須化）と、「エディタ編集後は CI とプレビューを確認する」の一文を AGENTS.md に足す。ステージング環境は現フェーズでは作らない（二重管理のコストがリターンを上回る。有料集客開始時に再評価）。
3. **リードデータの持ち出し経路の実測**（今すぐ・小）
   Lovable Cloud のバックアップ/復元/解約時ダンプの仕様は未確認。一度実際に試し、可能なら週次エクスポートを運用化する。

### 監視の空白（完全性チェックの発見）

- **本番の可観測性がゼロ**: `lovable-error-reporting.ts` は自らのコメントどおりエディタプレビュー内でしか機能せず、本番訪問者の JS エラー（フォームが描画されない等）はどこにも届かない。外形監視・死活監視もない。→ 軽い外形監視（無料枠の uptime 監視で可）＋週次の `notification_log` 確認から。
- **スタッフ認証が単要素のまま**: パスワードリセット経路がアプリに存在せず（`resetPasswordForEmail` 呼び出しゼロ）、MFA なしのパスワード 1 つが全リード PII の唯一の錠。ローンチ前に整備。
- **リード防衛コード自体が無検証**: `rescueUnsavedLead` 等の失敗経路にテストが 1 本もない。CI 緑は防衛線が動く保証ではない。
- **`SUPABASE_SERVICE_ROLE_KEY` 未設定時の静かな劣化**: `notification_log` 記録と重複検知は service role が無いと RLS により黙って無効化される。設定必須と明記し、未設定を管理画面に表示する（anon 向け insert ポリシーの追加は却下——バンドル内の anon キーで誰でも偽記録を書けるようになり監査ログが壊れる）。
- **ファネル計測が未接続**: `VITE_GA_MEASUREMENT_ID` / `VITE_META_PIXEL_ID` が未設定のため、実装済みの form_start/submit/error イベントはどこにも届いていない。ID を設定するだけ（経営判断）。
- **同意のバージョン証跡がない**: `privacy_agreed` は boolean 1 列で、その人が申込時に**どの版のポリシー・どの料金表示**を見たかを立証できない。料金確定・ポリシー改定は確実に起きるので、送信時に `policy_version`（git に紐づく版番号）を保存する列を足す（小）。

## 2. リード業務システム — フォーム系統は良い。LINE が外にいる

**維持**: ステータス 7 段階＋履歴＋作成者表示＋メモは 2 人運営に適正規模（かんばん化・担当者割当は増やさないこと）。滞留検知、URL フィルタ、匿名化、CSV の数式インジェクション対策も適切。

**変えるべきもの**:

1. **LINE 経由リードを DB に入れる手段がない**（最重要・high）
   管理画面にリードテーブルへの insert が一切存在しないことをコードで確認済み。CRM の真実が「DB（フォーム 3 種）」と「LINE トーク画面」に恒久的に割れ、LINE 側にはステータス・滞留検知・**削除請求対応（匿名化）**のどれも効かない。しかも contact ページは LINE をフォームより上に置いて積極誘導している。
   → **管理画面に手動登録フォーム＋ channel 列 1 本を追加**（utm 系の流入元列は既にあるので追加は channel のみ）。あわせて「相談として成立した時点で転記」「削除請求は DB 匿名化と LINE トーク削除をセット」の運用ルールを明文化。
2. **LINE アカウントの形態確認**（推測を含む・経営判断）
   `site.ts` の URL は `line.me/ti/p/〜` 形式で、一般に**個人アカウントの友だち追加リンク**に使われる形式（公式アカウントは通常 `lin.ee/〜`）。個人 LINE で受けているなら、リードの唯一の記録が特定個人の端末内トークになり、引き継ぎ・削除請求対応がすべて個人依存になる。要確認、必要なら公式アカウント化（無料プランから可能）。
3. **フルエクスポートが存在しない**（high）
   既存 CSV は部分列のみ（問い合わせ CSV は本文 message すら含まない・7 列）。**メモと対応履歴はエクスポート手段自体がない**。staff 認証＋service role の基盤は既にあるので、全テーブル全列の一括エクスポートは小さい追加。週次で実行し暗号化保管する運用とセットで。
4. **通知の足場固め**: `NOTIFY_EMAIL` の複数宛先対応（2 人運営の冗長性）、`notification_log` の失敗件数を概況カードに表示。LINE Messaging API での運営向け push は**現フェーズでは見送り**——メール整備後に見落としの実態が出てから判断（維持対象を増やすコストに見合わない）。
5. **滞留検知の拡張**（later・小）: 現状 `new` のみ対象。実運用の滞留は「確認中」「条件調整中」で起きるので、長め閾値（14 日等）で中間ステータスにも適用。

## 3. 将来の車両運用システム — 作らない。買う・人手で回す

`future.sql` の 16 テーブルは「予約・決済・GPS・契約を自社開発する」設計図として読むと**過大かつ誤導的**。実は content.ts のルールの最難部（クレジットの 24 か月ロット失効・遡及返還、年間枠の会計と譲渡、車両ごとの条件エンジン、重複予約防止）にはテーブルが存在しない——これは設計ではなくスケッチであり、その旨をファイル冒頭コメントに固定する（deny-all RLS 適用済みの現状の扱い自体は正しい）。

**ローンチ時の最小構成**（1 枚のドキュメントとして確定することを推奨・before-launch）:

| 領域                       | 作る/買う/人手                                                                                                                                                                                                    |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 名簿・審査・対応記録       | **既にある**（管理画面の延長）                                                                                                                                                                                    |
| 予約                       | 車両別共有カレンダー＋サーバータイムスタンプ付き申請フォーム（既存フォーム基盤流用）＋人手確定。「90 日前・完全先着順」の公開約束は**申請テーブルの created_at を先着基準**と規程に書けば予約システムなしで守れる |
| クレジット・枠・保証金台帳 | スプレッドシート（会員十数人なら月数十行）。ただし預り金台帳だけは**最初の入金日＝正式募集開始日**に必要                                                                                                          |
| 決済                       | **ホスト型 Stripe**（Payment Links/Billing）。カード情報を自社に触れさせない。ただし保証金 50 万〜200 万円は Stripe の与信ホールド期間を超えるため銀行振込＋台帳が濃厚——資金フローは専門家確認                    |
| 契約                       | 電子契約 SaaS＋一覧はスプレッドシート                                                                                                                                                                             |
| GPS・走行記録              | **SaaS 購入一択**。同意設計は LEGAL_TODOS どおり専門家確認へ                                                                                                                                                      |

**自動化の引き金となる閾値を先に決めておく**（目安: 車両 5 台 / 予約月 100 件 / クレジット取引月 50 件）。閾値超過時に最初に自動化すべきは予約 UI ではなく**クレジット台帳と枠管理**（整合性事故が最も起きやすい）。

## 4. 事業メカニズム — 開示は高水準。数字に構造的弱点が 2 つ

（この節はすべて経営判断・専門家確認の領域。サイトの掲載値からの指摘であり、法的助言ではない）

1. **OWNER NETWORK の受け渡し単価**（high・要実測）
   公開フローでは 1 予約に KSC の出動が最大 4 回付随する（鍵の事前受領→当日受け渡し→返却確認→鍵返却。車両は各オーナー保管のため）。1 出動 3,000〜7,500 円と仮定（**推測**）すると 4 出動＋通常洗車込みで 1 予約原価 1.5 万〜3.5 万円に対し、収入は 1 予約 1 万 1,000 円。反証側の留保: 出動は統合すれば 2〜3 回に圧縮でき、時給仮定も未検証——**よって「原価割れ」を断定して料金改定に走るのではなく、受け渡し 1 件の実原価を測り、月間利用回数×損益の感応表を作ってから決める**。`FEE_NOTE` が金額未確定と明示し、先行相談者がまだ金額にアンカーしていない今が変更の最安タイミング。COLLECTION 側の 5,500 円/予約も同じ検算対象。
2. **VALUE CHECK の固定費フロア**（high・社内規程で対処可能）
   共同オーナー 1 人の 3 年 KSC 固定費は約 114 万円（6 人・24 日想定: 入会 22 万＋月額 2.2 万×36＋予約料 5,500×24）。車両コストがゼロでも、単独所有 3 年総負担が約 229 万円（50%基準）/286 万円（40%目標）を下回る車両は構造的に不合格になる。反証側の留保: スーパーカーの単独所有側には保険・保管・整備の保有固定費だけで年 95 万円超の車両も多く、減価が小さくても基準を満たし得る。比較の分母定義も未確定。→ **固定費フロアの早期足切りを候補選定の最初に置き、閾値は車両クラス別の実データで検証してから確定**。保険引受条件の確定を VALUE CHECK 確定の前提条件にする（複数記名運転者の保険料は 40-50%比較の主要変数であり、引受可否自体が事業成立条件）。
3. **繁忙期の配分ルールが存在しない**（medium）
   「90 日前・完全先着順」は桜の枠が 1 月上旬のクリック競争で決まることを意味し、7 日前まで無料キャンセル（以降も別予約成立で返還）は**ピーク日の投機的確保を実質ノーコスト**にする。4〜8 人の少人数コミュニティでは紛争源。抽選・ピーク日上限・消化係数（ピーク 1 日=1.5 日分）等の選択肢から決め,`COLLECTION_USE_SPECS` に追記する。
4. **預り金台帳の必要時期は「最初の退出時」ではなく「最初の入金日」**
   正式募集開始と同時に、申込者ごとの預り金 50 万円について分別管理と 90(+30)日不成立返金の債務が発生する。分別口座と対をなす台帳（スプレッドシートで開始してよい——Supabase 上の台帳システム前倒し構築は過剰と反証済み）＋保全方法・未払い充当可否の専門家確認を、台帳実装より先に。

**維持すべきもの**: 確約しない表現規律、不利情報の先出し、参加申込預り金の分別・返金設計、持分と運転資格の分離（相続で破綻しない）、VALUE CHECK のゲート構造そのもの（未達なら見送る）、議決設計（全員/2/3/4/5 の使い分け）。
