# 改善提案（2026-08-29 時点のコードベース分析）

13 の分析エージェントでコードベース全体（公開サイト・フォーム・バックエンド/RLS・管理画面・SEO/計測・開発基盤）を精読し、生成した改善案は 1 件ずつ実コードと突き合わせて検証済み。行番号は分析時点のもの。

## このプロジェクトがやろうとしていること（読み取り）

京都を車両の保管・管理・受け渡し拠点とするスーパーカーブランドの**準備中フェーズのサイト**。いまの事業目的は 3 つ。

1. **共同オーナー候補のリード獲得**（KSC COLLECTION／無料の興味登録、契約・決済なし）
2. **既存オーナーのリード獲得**（KSC OWNER NETWORK／先行相談）
3. 許認可・保険・税務が未確定な段階で**補償・料金・車種・売却価格を確約しない**表現規律を守りつつ、正式募集時の信頼の土台を作ること

この読み取りを前提に、「予約・決済機能の追加」のようなフェーズ違反の提案は除外している。

### 現状の良いところ（維持すべき設計）

- 文言の単一ソース化（`content.ts`/`brand.ts`）が徹底され、金額・基準値のページ間矛盾は精査した範囲でゼロ
- 「計画です/予定です」の使い分け、LEGAL_BANNER、退出・相続・リスクを隠さない開示姿勢
- RLS は追補マイグレーションで適切に強化済み（anon は INSERT のみ、閲覧は `is_staff()` 経由で staff のみ）
- `LEGAL_TODOS` を非公開の内部チェックリストとして保持する自己認識の正確さ
- モバイル/a11y の実装品質（dvh・safe-area・44px タップ領域・skip link 等）

## S: 今すぐ直すべきもの（小さい修正で、実害・機会損失を止める）

### S-1. 広告流入ユーザーがフォーム送信不能になるバグの根絶

`attribution.ts:20-21` は landingPath（pathname+search 全体）と referrer を**無切り詰め**で保存し、`schemas.ts:223-231` の上限（utm 各 200 字 / landingPath・referrer 各 500 字）を超えると safeParse が失敗する。エラーは UI に存在しないフィールドに付くため、ユーザーには汎用トースト「入力内容を確認してください」しか見えず修正不能。**長いクエリ付き URL で流入した広告ユーザーが恒久的に送信ブロックされる。**

- `captureAttribution` で保存時に `slice()`、スキーマ側も `.catch("")` 等で attribution 起因では絶対に落とさない
- 併せて直す同種の離脱要因:
  - 電話・メールの**全角→半角正規化がない**（`schemas.ts:15`、IME で「０９０…」と入れると原因不明のエラー）。`z.preprocess` で NFKC 正規化
  - 希望メーカー/車種がヒント「未定でも構いません」なのに**必須**（`collection-form.tsx:230-256` + `schemas.ts:328-329`。サーバー側に「未定」フォールバックは既にある）
  - owner フォーム末尾の自由記述 2 つ（concerns / priorityUsePeriod）が必須。書くことがない高意向オーナーの離脱要因
  - Step2 表示中に Step1 所属のサーバーエラーが返ると画面上にエラーが存在しない → エラーキーが Step1 なら `setStep(1)` へ戻す（collection/owner 両フォーム）

### S-2. /collection に「投資ではない」注記を常設する

`INVESTMENT_NOTE`（`content.ts:20-21`）は定義済みなのに使用箇所は FAQ 回答 1 箇所のみ。/collection は再販 3 シナリオ・売却手数料 2.2%・「単独所有の 40〜50%」を詳述する**最も投資的に読まれやすいページ**で、`LEGAL_TODOS` の not-investment 項目（値上がり・利回りを約束しない）とも不整合。

- VALUE CHECK 直後か基本条件の冒頭に常設表示
- FAQ 抜粋に「投資になりますか？」を追加
- あわせて FAQ 抜粋の選定を**質問文字列ハードコード**（`index.tsx:137` / `collection.tsx:265` / `owners.tsx:219` の 3 箇所）から id 参照に変更。現状は質問文を一文字変えると該当 FAQ がサイレントに消える

### S-3. canonical の二重出力を止める（1 行級）

`__root.tsx:83-95` が fallbackHead の meta/links を常時展開するため、`seo.ts` の canonical（path: "/"）が**全サブページで各ページ専用 canonical と競合**する。検索流入の評価がトップに吸われるリスク。fallbackHead の links をルート head から外すだけで直る。

### S-4. 将来テーブル 16 本に RLS を有効化する

`20260827000001_future.sql` の members・vehicles・payments・contracts 等 16 テーブルに `enable row level security` が**一切ない**。Supabase では public スキーマのテーブルは既定で anon/authenticated に GRANT されるため、クライアントに埋め込まれる anon キーで読み書きできてしまう。中身が空の今のうちに deny-all（RLS 有効化のみ、ポリシーなし）の追補マイグレーションを足す。

### S-5. CI を 1 本入れ、孤立したユニットテストを接続する

- `package.json` の `test` は `check-kyoto.mjs` のみで、`schemas.test.ts`（実行すれば 7/7 合格）が**どこからも実行されない**
- `.github` 不在 = CI ゼロ。Lovable 連携によりこのブランチへの push は即エディタ・公開プレビューに同期される運用なのに、typecheck/lint/test のゲートがない
- 全チェック合計 30 秒未満なので GitHub Actions 1 本で塞がる。`test` は `node --test src/lib/*.test.ts && node scripts/check-kyoto.mjs` に（.ts 実行方法は要確認）

## A: リードの取りこぼしと信頼の穴（事業インパクト大）

### A-1. 送信完了体験を「次に何が起きるか」+ LINE 導線付きに作り替える

`SuccessPanel`（`form-status.tsx:4-19`）は「トップへ戻る」のみ。preferLine チェックボックスまで取っているのに完了画面に LINE 友だち追加導線がなく、獲得した高意向リードとの継続接点を捨てている。`contact.tsx:34-58` に LINE QR + 「契約や購入申込ではありません」コピーの実装が既にあり流用可能。

- 完了画面に: 今後の流れ（確認→個別連絡）/ LINE 友だち追加 / 受付 ID
- **本人宛の自動返信メール**を追加（現状は運営宛のみで、登録者側に証跡が一切残らない）。内容は要点+「契約・決済は一切発生していません」の再確認とし、入力内容の全文転記は避ける（個人情報最小化）。Resend の検証済みドメインが前提

### A-2. リード通知の信頼性（静かに死ぬ単一障害点を潰す)

`notify()`（`cloud.server.ts:87-104`）は (1) RESEND_API_KEY/NOTIFY_EMAIL 未設定なら黙ってスキップ、(2) 失敗は `catch {}` で完全に握りつぶしログなし、(3) タイムアウトなしで Resend 遅延がフォーム応答遅延に直結、(4) 既定差出人 `noreply@resend.dev` は Resend のサンドボックスで**本番ではほぼ配送されない**。

- 失敗を console.error + 既存の `notification_log` テーブル（定義済み・未使用）に記録
- `AbortSignal.timeout` を付け、通知は応答をブロックしない
- 新旧カラム insert フォールバック（`cloud.server.ts:211-215`）が失敗理由をログせず新列 11 項目を黙って落とし続ける問題も同時に可視化する
- 本番で Supabase 未設定だとリードが完全消失する経路（`localDevInsert` が UNCONFIGURED を返すだけ）に、notify へフル内容を送る最終退避を用意

### A-3. 「誰が運営しているのか」を見せる

運営者情報は `operator.ts` で全項目空欄（意図的: 法的確定まで非表示）で、公開サイトに運営者・About が**ゼロ**。高額商材の事前登録を求めるサイトとして最大級の信頼障壁。ただし空欄設計は意図的な判断なので、実施は経営判断: 法人名確定前に出せる範囲（活動の経緯・準備状況・写真）と、特商法表記・責任主体表示との整合を専門家確認とセットで検討する。

### A-4. 第二セグメント（既存オーナー）の導線欠落を塞ぐ

- デスクトップヘッダー CTA は「共同購入の興味登録」1 本のみ（`shell.tsx:79-90`）。オーナー向けの控えめな導線（テキストリンク可）を追加
- トップ末尾 CTA は本文で先行相談に言及しつつボタンは collection と LINE のみ（`index.tsx:163-181`）
- `apply/member.tsx` は本文で先行相談に言及しながらリンクは /collection のみ。/owners を追加し、ほぼ同一内容の `membership.tsx` と一本化（片方リダイレクト）

### A-5. 計測の統一（LINE 導線が丸ごと計測不能）

- LINE sticky（`shell.tsx:233-242`）・`InquiryCta`・contact ページの LINE アンカーに `track()` がなく、**2 大リード経路の片方が計測ゼロ**。collection は form_start がなく owner は submit まで揃うなど、イベント設計も非対称でファネル分析ができない
- Meta Pixel は初回 PageView のみで SPA 遷移時に送られない（`analytics.tsx:26`）。ルーター購読で遷移時 PageView を送る
- 注意: LINE 友だち追加 URL へのクエリパラメータ計測は LINE 側機能の制約があり、安易に手順化しない

### A-6. 管理画面に「対応漏れ防止」を入れる

少人数運営で最も起きやすい失敗（見た・忘れた）を防ぐ機構がゼロ。

- ダッシュボード: new 件数・「new のまま◯日経過」の強調。`getDashboardFn` は contacts を取得しているのに `recentContacts` を返しておらず、**最近欄にお問い合わせだけ存在しない**（`admin.ts:260-269`）
- 「要確認」台帳が表示専用: DB の status を読んでいるのに UI は固定ラベル「要確認」を描画（`admin.index.tsx:134-140`）。確認済み遷移・担当・確認日を記録できるようにする
- 一覧・詳細の実務: フィルタ状態の URL search params 化（戻るでリセットされる）、詳細画面に mailto:/tel:・コピー・返信テンプレート（「確約しない」方針の運用ガードにもなる）、メモ・履歴の author 表示、詳細画面の catch 欠落（失敗時に永久「読み込み中…」）

### A-7. プライバシー実務の整合

- ポリシーに GA4・Meta Pixel・Supabase・Resend・LINE の**具体名と保存期間がない**（`privacy.tsx:54-65` は抽象記述のみ）。`LEGAL_TODOS` 自身が要対応と認めている項目
- クッキー同意: 「同意しない」が保存されず**毎ロードでバナー再表示**（`analytics.ts:37-45` は false 時 removeItem のみ）。denied を永続化し、フッターに同意撤回導線を追加
- **個人情報削除の実行手段がない**: inquiry 系テーブルに DELETE ポリシーがなく、削除/匿名化機能も運用手順もない。窓口だけ書いて実行できない状態は個情法の開示・削除請求対応としてむしろリスク。service role による運用手順書か管理画面の匿名化機能を用意する

## B: 準備中フェーズの表現規律の穴（コピー・法務）

- **B-1. 準備中バナーの非対称**: `safety.tsx`（保険・事故負担という確約リスク最大のページ）と `faq.tsx`・`apply/collection.tsx` に PlanBanner/LEGAL_BANNER がない（`apply/owner.tsx:29` にはある）。保証金 aside の OWNER NETWORK 分「お預かりします」は断定調 → 予定調へ
- **B-2. 税込・税別の明確化**: 掲載中の予定額（22 万円/2.2 万円/2.2% 等）の税の扱いが不明。`LEGAL_TODOS` も「未確定」と自認。FEE_NOTE に一行追記して解釈を固定
- **B-3. 運転資格コピーの統一**: 「記名運転者/審査済み共同オーナー/登録本人」の用語揺れ（`content.ts:107-124` はタイトルと本文がずれ、同内容が 2 連続）。相続で運転しない持分のみの共同オーナーがあり得る設計と厳密には矛盾。1 定数に統一。京都拠点の「基本とします/です」のモダリティ揺れも同様
- **B-4. 実在メーカー名の alt**: 「ランボルギーニ・レヴエルト」等を alt で明示（4 ページ）しつつ非提携注記 PHOTO_NOTE はフッターのみ。注記を画像近くに置く。alt の完全中立化は視覚障害者への情報価値低下とのトレードオフがあるため「写真はイメージです」併記との組み合わせで設計
- **B-5. 未使用の COLLECTION_PHASE/PhaseChip**: 「いまは無料の興味登録」の意図した文言が実装から落ちている可能性。CTA 周辺で活用するか削除（注: 「無料」自体は COLLECTION_FEE_TIMING 経由で本文表示済み。重複させない）

## C: 技術負債・性能・堅牢化

- **C-1. PostgREST 直叩きスパム経路**: anon キーで直接 INSERT すれば Zod・ハニーポット・レート制限を全て迂回できる（レート制限自体もインメモリ Map + XFF 信頼で実効性が薄い）。まず DB 側に `char_length` の CHECK 制約を追加。anon INSERT ポリシーの削除（service role 経由へ一本化）は**本番に service role キーが常設されていることを確認してから**。前提が崩れると公開フォーム 4 種が全滅する
- **C-2. CSV/数式インジェクション**: `toCsv()`（`utils.ts:31-40`）が先頭 `= + - @` を無害化せず、公開フォーム由来の値をスタッフが Excel で開く導線がある。1 箇所の修正で全エクスポートに効く
- **C-3. 画像**: hero.webp（111KB）が未配線で hero.jpg（240KB）を配信、md5 一致の重複 4 組、未参照約 2.7MB、LINE QR が 1500px/204KB の JPEG（PNG なら数 KB で読み取り性も向上）、river.jpg 544KB は装飾なのに未圧縮。srcset/picture 対応も
- **C-4. デッドコード・未使用依存**: `member-form.tsx`（308 行・未参照）、`store.ts` の readDb/writeDb（約 200 行・未使用）、UI コンポーネント 47 個中 34 個が未参照、依存約 30 パッケージが未使用（recharts・react-hook-form 等）。`no-unused-vars` が off なのが症状と整合 → 再有効化
- **C-5. コントラスト（WCAG AA）**: copper 約 4.0:1・muted 約 3.4:1・cream/45 約 4.1:1 が小サイズテキストで未達。`styles.css` のトークン修正 1 箇所で全ページに効く。想定読者層（高年齢層含む）の可読性に直結
- **C-6. ドメイン移行の地雷**: `VITE_PUBLIC_SITE_URL` 未設定時に lovable.app へフォールバックするため、カスタムドメイン公開時の設定漏れで全 canonical/sitemap/OGP が旧ドメインを正典化。ビルド時警告 + `vite.config.ts` との定義一元化 + ローンチチェックリスト化
- **C-7. FAQ 構造化データ**: トップは 4 問表示なのに約 24 問の FAQPage を出力し、/faq と重複掲載（Google ガイドライン違反状態）。/faq のみに限定し表示内容と一致させる
- **C-8. Database 型生成**: `supabase gen types` → `createClient<Database>` で staff 認可コードの型裏付けを取る（現状は実質 any）
- **C-9. 重複リードの冪等性**: サーバー側の重複検出がなく、リトライ・再送で同一人物の重複リードが生成される。同一 email × フォーム種別のフラグ付けを推奨

## 保留（検討したが今はやらない判断も可）
