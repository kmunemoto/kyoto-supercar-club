# ローンチ時のシステム構成（作る / 買う / 人手）

`docs/SYSTEM_REVIEW.md` の第3節を、着手できる形に落としたもの。**車両 1〜3 台・会員十数人・運営 2 人**という初期条件が前提。

## 原則

1. **全予約に対面受け渡しが必ず付く。** ソフトウェアで削れる工数が構造的に小さい。ここが一般的なカーシェアと決定的に違う。
2. **金銭が動くものは自社実装しない。** 保証金 50 万〜200 万円・預り金 50 万円を扱うシステムの不整合は、そのまま金銭事故になる。
3. **`supabase/migrations/20260827000001_future.sql` は設計図ではない。** 一番難しいルール（クレジットの失効・遡及返還、年間枠の会計と譲渡）にテーブルが無い。SaaS を選ぶなら drop する。

## 割り当て表

| 領域                 | 方針                                    | 中身                                                                                                                                                  |
| -------------------- | --------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------- |
| 名簿・審査・対応記録 | **既にある**                            | `/admin` の一覧・詳細・ステータス・メモ・履歴。手動登録（`/admin/intake`）で LINE・電話経由も同じ器に入る                                             |
| 予約                 | **人手＋既存基盤**                      | 車両別の共有カレンダー（Google Calendar 等）＋利用申請フォーム＋人手で確定                                                                            |
| 先着順の立証         | **既存基盤**                            | 申請フォームのサーバー側 `created_at` を先着基準と規程に書く。公開約束の「90 日前・完全先着順」はこれで守れる                                         |
| クレジット・利用枠   | **人手（スプレッドシート）**            | 会員十数人なら月数十行。付与日・24 か月失効・消化を1行1イベントで追記                                                                                 |
| 預り金・保証金       | **人手＋分別口座**                      | **最初の入金日＝正式募集開始日に必要**。返金債務の管理が本体。保全方法は専門家確認（下記）                                                            |
| 決済                 | **買う（ホスト型 Stripe）**             | 入会金・月額・予約管理料は Payment Links / Billing で完結。カード情報を自社に触れさせない。`future.sql` の `payments.stripe_ref` はこの前提と既に整合 |
| 保証金の預かり       | **銀行振込＋台帳**                      | Stripe の与信ホールドは保持期間が短く、長期預かりには使えない。資金フローは専門家確認                                                                 |
| 契約                 | **買う（電子契約 SaaS）**               | 一覧はスプレッドシート。`future.sql` の `contracts` は実質ただの台帳                                                                                  |
| GPS・走行記録        | **買う（法人向けテレマティクス SaaS）** | 自社開発は選択肢に入れない。取得同意・保存期間・開示範囲は `LEGAL_TODOS` の gps 項目どおり専門家確認へ                                                |
| 受け渡し記録         | **人手＋共有ドライブ**                  | 写真は予約 ID ごとのフォルダ。`content.ts` が規定する対面フローがそのまま手順書                                                                       |

## 自動化に移る閾値

先に決めておき、超えるまで作らない。

- 車両 **5 台**
- 予約 **月 100 件**
- クレジット取引 **月 50 件**
- アクティブ会員 **30 人**

超えたとき、**最初に自動化するのは予約 UI ではなくクレジット台帳と枠管理**。整合性事故が起きるのはこちらで、予約は最後でよい。

理由: 予約ルールをまともに実装すると、二者間承認（48 時間期限）、失効付きクレジット台帳（24 か月・FIFO 消化・提供完了後付与）、時刻依存キャンセル精算（7 日前境界＋「別予約が入れば返還」の遡及処理）、車両×会員×年度の枠会計と譲渡、車両ごとの条件エンジンが必要になる。数人月規模＋保守（見積もりは推測を含む）。

## 専門家確認が前提のもの

台帳を実装する**前に**確認する。勘定設計と返金フローの前提になるため。

- 預り金・保証金の保全方法（口座分別で足りるか、信託等の要否、倒産隔離）
- 未払いへの保証金充当の可否と順序
- 位置情報の取得同意・保存期間・開示範囲
- 複数記名運転者・相互利用における保険の引受条件（`VALUE CHECK` 確定の前提条件でもある）

## 経営判断が必要なもの

- 繁忙期（桜・紅葉）の配分ルール。現行の「90 日前・完全先着順＋7 日前まで無料キャンセル」はピーク日の投機的確保を実質ノーコストにする。抽選 / ピーク日上限 / 年次ローテーション / 消化係数から選び、`COLLECTION_USE_SPECS` に追記する
- OWNER NETWORK の受け渡し単価。**実原価を 1 件測ってから**決める（`docs/SYSTEM_REVIEW.md` 第4節）
- `VALUE CHECK` の固定費フロアによる足切り閾値
